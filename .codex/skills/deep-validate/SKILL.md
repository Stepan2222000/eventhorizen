## Что ИСКАТЬ (критические ошибки)

| Категория | Примеры | Почему критично |
|-----------|---------|-----------------|
| `null-safety` | Обращение к None без проверки | Программа упадёт |
| `edge-case` | Пустой список, пустая строка, 0 | Неожиданное поведение |
| `logic-error` | Неправильное условие, off-by-one | Неверный результат |
| `race-condition` | Параллельный доступ без блокировки | Потеря данных |
| `resource-leak` | Файл/соединение не закрыто | Утечка ресурсов |
| `infinite-loop` | Цикл без выхода, рекурсия без базы | Программа зависнет |
| `data-loss` | Перезапись без проверки | Потеря данных |
| `error-handling` | Ошибка глотается без обработки | Скрытые проблемы |
| `state-corruption` | Состояние не восстанавливается | Некорректное состояние |
| `spec-mismatch` | Код не соответствует description в YAML | Спецификация врёт |
| `missing-binding` | Нет маркера @alg: для шага из YAML | Потеря трассировки |
| `wrong-binding` | Маркер в неправильном файле/функции | Путаница |

# ПАРАЛЛЕЛЬНАЯ РАБОТА АГЕНТОВ

**Несколько агентов работают над одним файлом ошибок одновременно.**

```
╔═══════════════════════════════════════════════════════════════════╗
║  ДРУГОЙ АГЕНТ МОЖЕТ ПЕРЕЗАПИСАТЬ ФАЙЛ — ЭТО НОРМАЛЬНО!            ║
║                                                                    ║
║  ПЕРЕД КАЖДОЙ ЗАПИСЬЮ:                                             ║
║  1. Перечитай файл ошибок (он мог измениться)                      ║
║  2. Merge свои находки с существующими                             ║
║  3. Запиши результат                                               ║
╚═══════════════════════════════════════════════════════════════════╝
```

## Алгоритм merge

**Для каждой своей находки:**

| Ситуация | Действие |
|----------|----------|
| Ошибка с таким `file` + `category` + похожим `problem` уже есть | Добавь свой `finding` в массив `findings`, увеличь `found_count` |
| Ошибки нет | Создай новую запись со своим finding |
| Твоя ошибка исчезла из файла | Не добавляй снова — её отклонили или исправили |

## Правила совместной работы

```
✅ ДЕЛАЙ:
   - Перечитывай файл перед записью
   - Добавляй свои findings к существующим ошибкам
   - Создавай новые записи для новых ошибок
   - Используй уникальный agent ID (validator-1, validator-2)

⛔ НЕ ДЕЛАЙ:
   - Не удаляй чужие записи
   - Не изменяй чужие findings
   - Не перезаписывай fix (это решает пользователь)
   - Не добавляй повторно удалённые ошибки
```

## Определение "та же ошибка"

Ошибка считается той же, если совпадают:
- `file` (тот же файл)
- `category` (та же категория)
- Суть `problem` (семантически похоже)

**Если сомневаешься** — добавь как отдельную ошибку. Лучше дубликат, чем потерянная находка.

## Категории архитектурных проблем (improvements):

| Категория | Что это | Примеры |
|-----------|---------|---------|
| `kiss-violation` | Overengineering, излишняя сложность | Абстракция ради абстракции, фичи "на будущее", сложная иерархия для простой задачи, нерациональный подход |
| `dry-violation` | Дублирование кода | Одинаковая логика в 2+ местах, copy-paste с минимальными изменениями |
| `suboptimal` | Не самое лучшее решение | Можно сделать проще/понятнее/эффективнее, неидиоматичный код |
| `dead-code` | Мёртвый код | Неиспользуемые функции, закомментированный код, недостижимые ветки |
| `naming` | Плохие имена | Непонятные имена переменных/функций, вводящие в заблуждение |

## Примеры архитектурных проблем:

### KISS Violation:
```yaml
- id: i-kiss01
  file: src/parser/factory.py
  category: kiss-violation

  issue: |
    ЧТО НЕ ТАК:
    Создан абстрактный Factory с 5 уровнями наследования
    для создания одного типа объекта (EbayClient).

    ПОЧЕМУ ЭТО ПЛОХО:
    - Используется только один конкретный класс
    - Абстракция не даёт никакой гибкости
    - Усложняет понимание и отладку

    КАК СДЕЛАТЬ ЛУЧШЕ:
    Просто создавать EbayClient() напрямую.
    Если понадобится второй клиент — тогда добавить абстракцию.
```

### DRY Violation:
```yaml
- id: i-dry01
  file: src/parser/handlers.py
  category: dry-violation

  issue: |
    ЧТО НЕ ТАК:
    Логика retry с exponential backoff дублируется в 4 местах:
    - fetch_item() строка 45
    - fetch_details() строка 89
    - fetch_images() строка 134
    - fetch_price() строка 178

    ПОЧЕМУ ЭТО ПЛОХО:
    - При изменении логики нужно менять в 4 местах
    - Легко забыть обновить одно из мест
    - Уже есть различия между копиями (баг?)

    КАК СДЕЛАТЬ ЛУЧШЕ:
    Вынести в декоратор @with_retry или функцию retry_request().
```

### Suboptimal:
```yaml
- id: i-sub01
  file: src/parser/search.py
  category: suboptimal

  issue: |
    ЧТО НЕ ТАК:
    Используется цикл с append вместо list comprehension:
    ```python
    results = []
    for item in items:
        if item.price > 0:
            results.append(item.name)
    ```

    ПОЧЕМУ ЭТО ПЛОХО:
    - Менее читаемо (больше строк)
    - Менее эффективно (множественные append)

    КАК СДЕЛАТЬ ЛУЧШЕ:
    ```python
    results = [item.name for item in items if item.price > 0]
    ```
```

1. **5 РАУНДОВ ОБЯЗАТЕЛЬНЫ** — нельзя пропускать ни один

6. **НЕ мелочи** — не security, не стиль, не .env
7. **Понятный язык** — человек должен сразу понять
8. **Перечитывай файл перед записью** — другой агент мог его изменить
