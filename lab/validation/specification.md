# EventHorizon — Как должно быть на самом деле

> **Дата:** 2026-02-07
> **Источник:** анализ ошибок + обсуждение с владельцем проекта
> **Назначение:** зафиксировать все решения о том, как система должна работать

---

## 1. Архитектура подключений к базе данных

Вся система управления подключениями через интерфейс — удаляется. Никакого UI для добавления, удаления, тестирования и конфигурирования подключений к базам данных. Никакого JSON-файла для хранения подключений. Никакого динамического создания пулов соединений на каждый запрос.

Вместо этого — две фиксированные базы данных, параметры подключения к которым задаются через переменные окружения (отдельные переменные для хоста, порта, имени базы, пользователя, пароля).

**Первая база — SMART-справочник** (parts_info). Содержит таблицу с каталогом запчастей. Приложение только читает из неё. Структура таблицы фиксированная и известна заранее: SMART-код, массив артикулов, название, бренд, описание. **При старте сервера загружается целиком в память и кэшируется.** Все обращения к справочнику идут через кэш, без повторных запросов к БД. Оперативки достаточно.

**Вторая база — inventory** (складской учёт). Содержит все таблицы, которые приложение создаёт и модифицирует самостоятельно: движения товаров, причины операций, способы доставки, представление остатков.

Для каждой базы создаётся один постоянный пул соединений при старте приложения, который живёт весь жизненный цикл процесса. Пулы должны иметь разумные таймауты на подключение, чтобы при недоступности базы приложение быстро сообщало об ошибке, а не зависало на минуты.

Если при старте приложения не удаётся подключиться к базе или создать необходимые таблицы — сервер должен остановиться с понятной ошибкой, а не продолжать работу в неисправном состоянии.

Всё, что связано с multi-DB функционалом, удаляется: страница управления подключениями, файл хранения подключений, логика динамического маппинга полей, все API-эндпоинты для работы с подключениями, пункт в навигационной панели.

---

## 2. SMART-код — основа всей системы

SMART-код — это уникальный идентификатор запчасти. У одной запчасти может быть несколько артикулов — это не разные написания одного и того же номера, а реально разные каталожные номера, которые относятся к одной и той же физической запчасти. Например, у одного SMART-кода может быть оригинальный артикул производителя, артикул из каталога TecDoc и артикул из внутреннего каталога поставщика.

**Для пользователя** удобно работать с артикулами — вводить их при поиске, видеть в списках. Артикул — это то, что человек обычно знает и вводит.

**Для системы** главным идентификатором является SMART-код. Вся бизнес-логика строится вокруг него:

- Остатки на складе считаются по SMART-коду, объединяя все движения по всем артикулам этого кода
- Аналитика прибыли группируется по SMART-коду — один товар = одна строка в рейтинге
- Сопоставление покупок и продаж для расчёта прибыли — по SMART-коду, а не по конкретному артикулу
- Проверка достаточности остатков при продаже — по SMART-коду
- Страница деталей товара показывает информацию по SMART-коду

Колонки `article` в таблице движений (`inventory.movements`) **нет**. Артикулы живут только в SMART-справочнике для поиска и отображения на экране — подтягиваются из серверного кэша по SMART-коду. В базе движений записывается только SMART-код, количество и остальные поля операции.

## 3. Типы операций

В системе пять типов операций:

### Покупка (purchase)
Поступление нового товара на склад. Количество всегда положительное. Обязательно указать цену закупки и номер коробки (свободный текст — физическая метка местоположения на складе) — это ключевые данные для аналитики и поиска товара на складе. Примечание опционально.

### Продажа (sale)
Отгрузка товара покупателю. Количество всегда отрицательное. Обязательно указать цену продажи и стоимость доставки — без этого невозможно посчитать прибыль. При бесплатной доставке (самовывоз и т.п.) указывается 0. Способ доставки и трек-номер тоже важны, но трек-номер может быть добавлен позже. Примечание опционально. При создании продажи ей автоматически присваивается статус "ожидает отправки".

### Возврат (return)
Возврат проданного товара на склад. Количество всегда положительное. Создаётся только через страницу "Проданные товары" (нажатием кнопки "Вернуть на склад"), а не через общую форму. Примечание формируется автоматически со ссылкой на номер исходной продажи. Финансовые поля не используются.

### Списание (writeoff)
Удаление товара из учёта (брак, потеря, утилизация). Количество всегда отрицательное. Финансовые поля не используются. Примечание опционально.

### Корректировка (adjust)
Операция приведения остатков в соответствие с реальностью. Используется когда при пересчёте склада фактическое количество расходится с данными в системе. Количество может быть и положительным (нашлись лишние штуки), и отрицательным (обнаружена недостача). Цена за единицу **опциональна** — можно указать стоимость каждой единицы (например, для оценки потерь при недостаче или стоимости найденных излишков). Примечание **обязательно** — пользователь должен объяснить причину расхождения, например: "Пересчёт склада, обнаружена недостача" или "Нашлись на другой полке". Сейчас корректировка удалена из системы — нужно вернуть.

## 4. Форма добавления движения

### Автокомплит
Одно поле поиска, которое принимает **и артикулы, и SMART-коды**. Пользователь вводит запрос → система ищет в кэшированном SMART-справочнике → выпадающий список с результатами (артикул, название, бренд) → пользователь выбирает → SMART-код записывается в движение. Артикул в базу **не сохраняется** — он нужен только для поиска. Если пользователь продолжает печатать, предыдущий незавершённый запрос поиска должен отменяться, чтобы устаревшие результаты не перезаписали актуальные. Сейчас этой защиты нет — при быстром вводе результаты могут приходить в неправильном порядке.

### Условные поля
В зависимости от выбранного типа операции показываются разные поля:
- Покупка — цена закупки, номер коробки
- Продажа — цена продажи, стоимость доставки, способ доставки, трек-номер
- Корректировка — цена за единицу опциональна, примечание обязательно
- Списание — никаких финансовых полей

Когда пользователь переключает тип операции, значения скрытых полей должны очищаться. Сейчас они остаются в памяти формы и могут случайно отправиться на сервер. На сервере тоже должна быть защита — игнорировать нерелевантные поля в зависимости от типа операции.

### Предзаполнение из URL
Когда пользователь переходит на форму из другой страницы (например, со страницы остатков по кнопке "+"), SMART-код предзаполняется из URL-параметра `smart`. Параметр `article` в URL не нужен — артикулы не сохраняются в движениях.

### Обновление кэша
После успешного создания движения нужно обновить все связанные кэши: список движений, остатки, статистику дашборда, покупки и продажи по конкретному SMART-коду, рейтинг товаров, список проданных товаров. Сейчас обновляются только три кэша из семи, и из-за настройки "данные никогда не устаревают" пользователь видит старую информацию до перезагрузки страницы.

---

## 5. Страница остатков

Должны загружаться все позиции, без искусственного ограничения. Сейчас показывается максимум 50 записей, и пользователь даже не знает, что остальные существуют. Пагинация не нужна — загрузить всё, фильтрация и сортировка на клиенте.

Товары с нулевым остатком не показываются — представление (VIEW) в базе уже исключает их. Товары с нулевым остатком видны на отдельной странице "Sold Out".

Кнопка "+" рядом с каждой позицией передаёт на страницу создания движения только SMART-код. Артикул для отображения подтягивается из кэша SMART-справочника.

Значения остатков, приходящие из базы, могут быть строками вместо чисел (особенность драйвера PostgreSQL для больших чисел). Нужно явно приводить к числу, иначе сравнения и арифметика могут работать неправильно.

---

## 6. Аналитика и рейтинг товаров

Рейтинг товаров должен группироваться по SMART-коду, а не по паре SMART-код + артикул. Один SMART-код — одна строка в рейтинге. Сейчас один товар может появиться несколько раз (если продавался под разными артикулами), что создаёт дубликаты в таблице и вызывает ошибки отрисовки.

Средняя цена закупки считается по **всем** покупкам данного SMART-кода (по всем артикулам). Сейчас SQL-запрос фильтрует покупки по конкретному артикулу (`WHERE p.smart = s.smart AND p.article = s.article`), что неправильно — нужно только по SMART-коду. Также в запросе присутствует мёртвый код `ORDER BY p.purchase_date DESC LIMIT 10`, который не влияет на результат `AVG()`, но вводит в заблуждение.

Сопоставление покупок и продаж для расчёта прибыли — по SMART-коду, а не по артикулу. Раз артикулы одного SMART-кода — это одна запчасть, то любая покупка может быть сопоставлена с любой продажей в рамках одного SMART-кода.

**Формула прибыли за единицу:** `цена_продажи − средняя_цена_закупки − стоимость_доставки`. На странице деталей товара показываются все покупки и продажи по данному SMART-коду, независимо от артикула.

---

## 7. Проданные товары

### Статус продажи
При создании продажи сервер должен автоматически устанавливать статус "ожидает отправки". Не полагаться на то, что клиент передаст правильный статус.

Продажи без статуса (значение не заполнено) должны показываться вместе с "ожидающими отправки", а не исчезать из обоих списков. Сейчас такие продажи невидимы и неуправляемы.

### Защита от ошибок
Обновление статуса продажи должно проверять, что операция действительно является продажей. Сейчас можно установить статус "отправлено" для покупки или списания, что семантически бессмысленно.

### Отладочные сообщения
Убрать отладочные console.log, оставленные в коде мутации возврата.

---

## 8. Поиск артикулов

При переходе к созданию движения из результатов поиска передаётся только SMART-код. Артикул не записывается в движение.

Модальное окно выбора (disambiguation) должно закрываться при начале нового поиска. Сейчас если первый поиск показал модалку, а второй вернул один результат — модалка остаётся открытой с данными от первого поиска.

---

## 9. Детали товара и нулевой остаток

Если товар был на складе, но полностью продан (остаток = 0), API должен возвращать объект с нулевым остатком, а не ошибку "не найдено". Нулевой остаток — это валидное состояние ("всё продано"), а не отсутствие данных. Ошибка 404 должна возвращаться только если SMART-код вообще никогда не проходил через систему.

---

## 10. Дашборд

Запчастей немного — загружать все данные без искусственного лимита. Сейчас жёсткий `limit = 1000` обрезает данные, и показатели могут быть занижены. Убрать лимит, загружать все остатки и движения. При большом объёме обрабатывать батчами.

---

## 11. Кэширование

Данные в приложении не устаревают автоматически — обновление происходит только когда пользователь совершает действие (создание движения, смена статуса и т.д.). Этот подход нормален для однопользовательского приложения, но требует, чтобы инвалидация кэшей после каждого действия была **полной** — все затронутые страницы должны получить свежие данные. Сейчас инвалидация неполная, и страницы могут показывать устаревшую информацию.

---

## 12. Импорт данных

Файл импорта должен содержать SMART-код — это обязательное поле. Система не должна гадать, какой SMART-код имелся в виду по артикулу (возможны неоднозначности). Минимальный набор полей: SMART-код, количество, тип операции. Артикул в импорте не требуется — он не сохраняется в движениях.

CSV-парсинг должен корректно обрабатывать кавычки и запятые внутри полей. Сейчас наивное разбиение по запятой ломает данные, если поле содержит запятую.

При импорте Excel-файлов нужно проверять, что файл не пуст и содержит хотя бы один лист. Числовые артикулы из Excel нужно приводить к строке.

Строки, которые не прошли валидацию при импорте, не должны молча исчезать. Пользователь должен видеть, какие именно строки были пропущены и почему.

Размер загружаемых файлов должен быть ограничен (например, 10 МБ), чтобы очень большой файл не мог исчерпать память процесса.

---

## 13. Обработка ошибок

Инфраструктурные ошибки (база данных недоступна, таймаут, сетевой сбой) не должны маскироваться как ошибки клиента (HTTP 400). Пользователь должен понимать, что проблема на стороне сервера.

Ошибки при получении данных об остатках не должны маскироваться как нулевые остатки. Если база данных недоступна, лучше показать ошибку загрузки, чем ложную информацию "0 на складе" для всех товаров. Принятие решений на основе неверных данных опаснее, чем временная недоступность.

---

## 14. Прочее

**Дублирование кода.** Функция нормализации артикулов существует в двух копиях — нужна одна общая. Маппинг строки из базы данных в объект JavaScript повторяется в каждом методе — нужен один helper. Инициализация схемы базы данных выполняется в двух местах с разными данными — нужно одно место.

**Зависимость подписки в useToast.** Эффект подписки на уведомления пересоздаётся при каждом обновлении состояния, хотя должен создаваться один раз.

**Недостижимый код.** В обработчике возврата товара есть ветка для ошибки "недостаточно остатков", но возврат увеличивает остаток и эта ошибка невозможна.

### e-042: BIGINT из PostgreSQL может прийти строкой

**Файл:** `server/storage.ts`, строки 628, 688
**Уверенность:** Высокая (4/4 агента согласны)

**Как сейчас работает:**
В `getStockLevels()` значение `totalQty` берётся напрямую из результата SQL-запроса: `totalQty: row.total_qty`. VIEW `inventory.stock` определяет `total_qty` как `SUM(qty_delta)`. В PostgreSQL сумма INTEGER-колонки имеет тип BIGINT. Драйвер `pg` для Node.js возвращает BIGINT как строку (не как число), потому что JavaScript-числа не могут точно представить все значения BIGINT. В итоге `totalQty` может оказаться строкой `"42"` вместо числа `42`. Тип `StockLevel` в `shared/schema.ts` объявляет `totalQty: number`, но в рантайме это может быть строка. Сравнения типа `totalQty > 0` или `totalQty === 0` могут работать непредсказуемо.

**Как должно работать:**
Значение `total_qty` должно явно приводиться к числу: `totalQty: Number(row.total_qty)` или `totalQty: parseInt(row.total_qty)`. Альтернативно, в SQL можно использовать каст: `SUM(qty_delta)::int as total_qty` (если значения гарантированно помещаются в INTEGER).
