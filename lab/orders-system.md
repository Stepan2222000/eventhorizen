# Система заказов и клиентов — Детальное описание

> **Дата:** 2026-02-09
> **Назначение:** описать, как должна работать новая система заказов, клиентов, отправок и возвратов
> **Статус:** проект (требует утверждения перед реализацией)

---

## 1. Зачем это нужно

Сейчас система — это плоский журнал складских движений. Каждая продажа — отдельная запись, не связанная ни с клиентом, ни с другими продажами. Это создаёт проблемы:

- Невозможно узнать, кому продали товар
- Невозможно сгруппировать товары, проданные одному человеку
- При продаже нескольких товаров в одной посылке нужно заполнять данные доставки заново для каждого товара
- Стоимость доставки дублируется в каждой записи, хотя оплачивается один раз за посылку
- Возврат — это создание нового движения с текстовой ссылкой на номер исходной продажи (парсинг строки "Возврат продажи #42"), что хрупко и не позволяет частичный возврат
- Непонятно, кто платит за доставку (мы или покупатель) — а это влияет на расчёт прибыли
- Нет различия между "отправили почтой" и "клиент забрал сам"

Новая система вводит сущности **клиент**, **заказ**, **отправка** и **возврат**, чтобы все эти проблемы решить.

---

## 2. Общая философия

Покупки (`purchase`), списания (`writeoff`) и корректировки (`adjust`) **не меняются**. Они остаются простыми движениями в `inventory.movements`. У них нет клиента, заказа или отправки — это внутренние складские операции.

Продажи (`sale`) и возвраты (`return`) **переходят на новую модель**. Вместо прямого создания движения через форму, пользователь создаёт **заказ** с позициями, а движения создаются автоматически.

Таблица `inventory.movements` остаётся **источником истины для остатков**. Все остатки по-прежнему считаются через `SUM(qty_delta)` по SMART-коду. Новые таблицы — это слой управления продажами поверх движений.

## 3. Сущности

### 3.1 Клиенты (`inventory.customers`)

Клиент — это человек, которому мы продаём товары. Минимум данных:

- **Имя** — обязательное. Как угодно: "Иван", "Петров И.А.", "avito_buyer_2024". Главное — чтобы пользователь мог отличить одного клиента от другого.
- **Телефон** — опциональный. Для связи и идентификации.
- **Заметка** — опциональный. Свободный текст: "постоянный клиент", "просит звонить перед отправкой", "скидка 5%".

Адрес **не хранится** на уровне клиента. Один клиент может просить доставку в разные места — адрес привязывается к конкретной отправке (если когда-нибудь понадобится поле адреса). Сейчас для адреса достаточно заметки в заказе.

Клиенты не удаляются — только архивируются (чтобы история заказов не ломалась).

### 3.2 Заказы (`inventory.orders`)

Заказ — это группа товаров, проданных одному клиенту за раз. Один клиент может иметь много заказов.

- **Ссылка на клиента** — обязательная.
- **Заметка** — опциональная. "Просил упаковать отдельно", "оплата при получении".
- **Дата создания** — автоматическая.

Заказ сам по себе не содержит сумм, цен, статусов доставки. Всё это определяется через позиции и отправки.

### 3.3 Позиции заказа (`inventory.order_items`)

Каждая позиция — это один SMART-код с количеством и ценой за единицу.

- **Ссылка на заказ** — обязательная.
- **SMART-код** — обязательный. Какой товар.
- **Количество** — обязательное, положительное целое число. Сколько штук.
- **Цена продажи за единицу** — обязательная. В рублях за одну штуку.

Одна позиция порождает одно движение в `movements` с `reason = 'sale'` и `qty_delta = -количество`.

Артикулы, название, бренд — **не хранятся** в позиции. Они подтягиваются из SMART-кэша при отображении (как и сейчас в movements).

### 3.4 Отправки (`inventory.shipments`)

Отправка — это одна физическая посылка или один самовывоз. К одному заказу может быть несколько отправок (например, часть товаров отправили сразу, часть — через неделю).

- **Ссылка на заказ** — обязательная.
- **Способ доставки** — обязательный. Ссылка на `shipping_methods`. Включая "Самовывоз".
- **Трек-номер** — опциональный. Для самовывоза обычно пуст.
- **Стоимость доставки** — обязательная. Это стоимость **за всю посылку** (за отправку), не за единицу товара. Для самовывоза обычно 0.
- **Кто платит за доставку** — обязательный. Два варианта: "продавец" или "покупатель". Влияет на расчёт прибыли.
- **Статус** — обязательный. Жизненный цикл отправки (описан ниже).
- **Дата создания** — автоматическая.

#### Самовывоз как способ доставки

"Самовывоз" — это один из способов доставки в таблице `shipping_methods`. Добавляется в список дефолтных при инициализации (наряду с "Почта России", "Яндекс", "СДЭК", "Авито доставка").

Когда пользователь выбирает "Самовывоз" в форме:
- Поле трек-номера скрывается или становится неактивным (трека нет)
- Стоимость доставки подставляется 0 (можно изменить, если самовывоз платный)
- Поле "кто платит" скрывается (неактуально при нулевой стоимости)
- Статус отправки сразу устанавливается в "получено" (товар забрали на месте)

Чтобы система знала, какой способ является самовывозом, в таблицу `shipping_methods` добавляется флаг `is_pickup`. Это позволяет UI автоматически настраивать форму при выборе такого способа.

#### Статусы отправки

Для обычной доставки (не самовывоз):
1. **ожидает отправки** (`pending`) — товар собран, ждёт отправки
2. **отправлено** (`shipped`) — посылка передана перевозчику
3. **доставлено** (`delivered`) — покупатель получил (опциональный статус, если хотим отслеживать)

Для самовывоза:
- Сразу устанавливается статус **получено** (`delivered`) — клиент забрал товар

### 3.5 Содержимое отправки (`inventory.shipment_items`)

Связь "что в какой посылке". Нужна потому, что один заказ может быть разбит на несколько отправок.

- **Ссылка на отправку** — обязательная.
- **Ссылка на позицию заказа** — обязательная.
- **Количество** — обязательное. Сколько штук из этой позиции попало в эту посылку.

Пример: заказ из 5 деталей (3 колодки + 2 фильтра). Колодки отправляем сейчас, фильтры — через неделю. Две отправки:
- Отправка 1: колодки, 3 шт, СДЭК, трек RA123, 350 ₽
- Отправка 2: фильтры, 2 шт, Почта России, трек RP456, 250 ₽

Сумма количеств в отправках не может превышать количество в позиции (нельзя "отправить больше, чем заказано").

### 3.6 Возвраты (`inventory.returns`)

Возврат — это событие, когда покупатель возвращает часть или все товары из заказа.

- **Ссылка на заказ** — обязательная. Всегда знаем, из какого заказа возврат.
- **Заметка** — опциональная. Причина возврата: "не подошла по размеру", "брак", "передумал".
- **Стоимость обратной доставки** — обязательная (0 если нет доставки, например возврат при самовывозе).
- **Кто платит за обратную доставку** — обязательный. "Продавец" или "покупатель". Влияет на расчёт прибыли.
- **Способ обратной доставки** — опциональный. Ссылка на `shipping_methods`.
- **Трек-номер обратной доставки** — опциональный.
- **Дата создания** — автоматическая.

### 3.7 Позиции возврата (`inventory.return_items`)

Какие именно товары вернули и в каком количестве.

- **Ссылка на возврат** — обязательная.
- **Ссылка на позицию заказа** — обязательная. Чтобы знать, какой именно товар возвращён.
- **Количество** — обязательное. Сколько штук вернули.

Возврат может быть **частичным**: из 3 заказанных колодок вернуть только 1. Сумма возвращённых штук по всем возвратам не может превышать количество в исходной позиции (нельзя "вернуть больше, чем купил").

Каждая позиция возврата порождает движение в `movements` с `reason = 'return'` и `qty_delta = +количество` (товар возвращается на склад).

## 4. Связь с существующей таблицей `movements`

Таблица `inventory.movements` **остаётся центром системы** для учёта остатков. Но теперь в ней появляются дополнительные ссылки:

- **`order_id`** — ссылка на заказ (для продаж и возвратов). Для покупок, списаний и корректировок — NULL.
- **`order_item_id`** — ссылка на конкретную позицию заказа (для точной привязки).
- **`shipment_id`** — ссылка на отправку (для продаж). Если товар ещё не отправлен — NULL.
- **`return_id`** — ссылка на возврат (для возвратов). NULL для остальных.

Все эти поля **nullable**. Существующие данные в таблице остаются без изменений — у них все новые поля будут NULL. Новые продажи и возвраты будут создаваться через заказы и иметь заполненные ссылки.

Поля `sale_price`, `delivery_price`, `track_number`, `shipping_method_id`, `sale_status` в таблице movements **становятся устаревшими** для новых записей. Цена продажи берётся из `order_items.sale_price`. Доставка — из `shipments.delivery_price`. Трек и способ — из `shipments`. Статус — из `shipments.status`. Но для обратной совместимости со старыми записями эти колонки не удаляются.

### Что происходит при создании заказа

1. Пользователь создаёт заказ: выбирает клиента, добавляет позиции (SMART, кол-во, цена), настраивает отправку.
2. Система создаёт записи: `orders` → `order_items` → `shipments` → `shipment_items`.
3. Для каждой позиции заказа **автоматически** создаётся `movement`:
   - `smart` = SMART-код позиции
   - `qty_delta` = минус количество (расход со склада)
   - `reason` = 'sale'
   - `sale_price` = цена из позиции (для обратной совместимости)
   - `order_id`, `order_item_id` = ссылки на заказ и позицию
   - `sale_status` = берётся из статуса отправки
4. Остатки обновляются автоматически (через VIEW на movements).

### Что происходит при возврате

1. Пользователь открывает заказ, нажимает "Возврат".
2. Выбирает какие позиции и сколько штук вернуть.
3. Указывает стоимость обратной доставки и кто платит.
4. Система создаёт записи: `returns` → `return_items`.
5. Для каждой позиции возврата **автоматически** создаётся `movement`:
   - `smart` = SMART-код позиции
   - `qty_delta` = плюс количество (приход на склад)
   - `reason` = 'return'
   - `order_id`, `order_item_id`, `return_id` = ссылки
6. Остатки обновляются автоматически.

## 5. Семантика цен

Это важный момент, который сейчас нигде явно не описан.

### Цена закупки (`purchase_price`) — ЗА ЕДИНИЦУ

Пользователь вводит цену одной штуки при покупке. Если купил 10 колодок по 500 ₽ — вводит 500, не 5000.

В интерфейсе должно быть: метка **"Цена закупки за ед."** + подсказка с вычисленным итогом **"Итого: {цена × кол-во} ₽"** (аналогично тому, как уже сделано для цены продажи).

### Цена продажи (`sale_price`) — ЗА ЕДИНИЦУ

Пользователь вводит цену одной штуки при продаже. Уже подписано "Цена за единицу товара" и есть подсказка "Общая сумма".

### Стоимость доставки (`delivery_price`) — ЗА ВСЮ ОТПРАВКУ

Это стоимость одной физической посылки. Не за штуку, не за единицу — за отправку целиком. Ты платишь перевозчику одну сумму за одну коробку, неважно сколько деталей внутри.

В новой системе `delivery_price` живёт в таблице `shipments`, а не в `movements`. Одна отправка — одна стоимость. Никакого дублирования.

### Стоимость обратной доставки (`return_price`) — ЗА ВЕСЬ ВОЗВРАТ

Аналогично — это сумма, которую стоит доставка возвращаемого товара обратно. Одна сумма за одну обратную посылку.

### Кто платит

У каждой отправки и каждого возврата есть поле "кто платит": **продавец** или **покупатель**.

- Если платит **покупатель** — это не наш расход, не влияет на нашу прибыль
- Если платит **продавец** (мы) — это наш расход, вычитается из прибыли

## 6. Формула прибыли

### По одному заказу

```
прибыль = доход_от_продаж − себестоимость − наши_расходы_на_доставку

доход_от_продаж = сумма(цена_продажи × количество) по всем позициям заказа
себестоимость = сумма(средняя_цена_закупки × количество) по всем позициям заказа (по SMART-коду)
наши_расходы_на_доставку = сумма(стоимость_доставки) по отправкам, где платит продавец
                         + сумма(стоимость_возврата) по возвратам, где платит продавец
```

Средняя цена закупки считается как **средневзвешенная по всем покупкам** данного SMART-кода (то есть `SUM(purchase_price × qty) / SUM(qty)` по всем purchase-движениям с этим SMART-кодом).

### По товару (для рейтинга)

Для рейтинга "лучших товаров" прибыль группируется по SMART-коду. Учитываются все заказы, в которых есть позиции с данным SMART-кодом. Расходы на доставку распределяются пропорционально стоимости товаров в посылке (если в одной посылке несколько разных товаров).

### Исправление текущего бага

Сейчас формула считает `profit = (salePrice - avgPurchase - deliveryPrice) × qty`, что неверно: `deliveryPrice` — это за всю посылку, а не за единицу. Это приводит к многократному вычитанию доставки при `qty > 1`.

Правильная формула: `profit = (salePrice - avgPurchase) × qty - deliveryPrice` (если платим мы) или `profit = (salePrice - avgPurchase) × qty` (если платит покупатель).

## 7. Существующие данные

Все текущие записи в `inventory.movements` **сохраняются без изменений**. Они нужны для тестирования и для истории.

У старых записей поля `order_id`, `order_item_id`, `shipment_id`, `return_id` будут NULL — это нормально.

Старые продажи продолжат отображаться в истории движений. Они просто не будут привязаны к заказам. При необходимости можно добавить возможность "привязать" старую продажу к клиенту/заказу, но это не обязательно для первой версии.

Страница "Проданные товары" (`sold-items`) должна показывать:
- Новые продажи — через заказы (с группировкой по клиенту, позициям, отправкам)
- Старые продажи — в отдельной секции "Без заказа" (как сейчас, по плоским движениям)

## 8. Интерфейс

### 8.1 Новая страница: Клиенты

Список всех клиентов с возможностью:
- Добавить нового клиента (имя, телефон, заметка)
- Найти клиента по имени или телефону
- Посмотреть историю заказов клиента (переход на страницу клиента)
- Отредактировать данные клиента

На странице конкретного клиента:
- Его данные (имя, телефон, заметка)
- Список всех его заказов с кратким описанием (дата, количество позиций, сумма, статус)
- Общая статистика: сколько заказов, на какую сумму, сколько возвратов

### 8.2 Форма создания заказа (переделка формы продажи)

Сейчас форма добавления движения при выборе "Продажа" показывает поля для одного товара. Нужно переделать в мульти-товарную форму.

Верхняя часть: **выбор клиента**
- Автокомплит по имени/телефону
- Кнопка "Новый клиент" (быстрое создание прямо из формы)

Средняя часть: **позиции заказа** (динамический список)
- Каждая строка: поиск SMART + количество + цена за единицу
- Кнопка "Добавить ещё товар"
- У каждой строки кнопка удаления
- Внизу списка: итого количество, итого сумма

Нижняя часть: **отправка**
- Способ доставки (выпадающий список, включая "Самовывоз")
- Трек-номер (скрывается при самовывозе)
- Стоимость доставки (по умолчанию 0 для самовывоза)
- Кто платит (продавец / покупатель, скрывается при стоимости 0)

При самовывозе (когда выбран способ с флагом `is_pickup`):
- Трек-номер скрывается
- Стоимость доставки = 0
- Поле "кто платит" скрывается
- Статус сразу "получено"

Итоговый блок: общая сумма товаров + доставка = общий итог

Кнопка "Оформить заказ" создаёт всё сразу: заказ, позиции, отправку, содержимое отправки, движения.

Для простого случая (1 товар, 1 отправка) форма не сложнее текущей — просто добавляется выбор клиента сверху.

### 8.3 Переделка страницы "Проданные товары"

Сейчас: два списка карточек — "Ожидает отправки" и "Отправлено". Каждая карточка — одно движение.

Новый формат: список **заказов**, каждый раскрывается в детали.

Карточка заказа показывает:
- Клиент (имя)
- Дата заказа
- Количество позиций, общая сумма
- Статус отправок (сколько отправлено, сколько ждёт)

При раскрытии заказа:
- Список позиций (SMART, название, кол-во, цена, итого по позиции)
- Список отправок с их статусами и содержимым
- Кнопка "Отправлено" для каждой отправки (сменить статус)
- Кнопка "Возврат" — открывает форму частичного возврата

Старые продажи (без `order_id`) показываются в отдельной секции внизу, как раньше.

### 8.4 Форма возврата

Открывается из детали заказа. Показывает список позиций заказа с возможностью выбрать, что и сколько вернуть:


### 8.5 Страница деталей заказа

Новая страница, доступная по клику на заказ из списка проданных или из страницы клиента.

Показывает:
- Данные клиента (имя, телефон)
- Все позиции заказа
- Все отправки с их статусами и содержимым
- Все возвраты с деталями
- Финансовая сводка: сумма продаж, себестоимость, расходы на доставку, прибыль

Таблица продаж — сейчас показывает отдельные движения с ценами. Нужно обновить:

## 12. Что НЕ входит в эту систему

- **CRM-функционал**: маркетинг, рассылки, воронки продаж — это не складской учёт
- **Адресная книга**: хранение адресов клиентов — пока не нужно, достаточно трек-номера
- **Оплата**: система не отслеживает факт оплаты, задолженности, счета — это бухгалтерия
- **Скидки**: нет системы скидок, ценовых правил — пользователь просто вводит нужную цену
- **Автоматическое ценообразование**: цены устанавливаются вручную
