# Система учёта коробок (мест хранения) — полная спецификация

## 1. Цель и бизнес-контекст

Система складского учёта EventHorizon оперирует SMART-кодами — уникальными идентификаторами запчастей. Сейчас система знает **сколько** товара на складе, но не знает **где именно** он физически находится.

Поле `box_number` уже существует в таблице `movements`, но используется только при покупках как текстовая метка. При продажах, списаниях, возвратах и корректировках коробка не указывается. Из-за этого невозможно ответить на вопрос "что лежит в коробке K-4?" — потому что продажи не привязаны к конкретным коробкам.

Задача: внедрить полноценную систему учёта содержимого коробок, позволяющую в любой момент узнать что находится в каждой коробке и перепроверить это физически (инвентаризация).

---

## 2. Архитектурные решения

### 2.1. Источник истины — таблица movements

Содержимое каждой коробки не хранится в отдельной таблице, а **вычисляется** из истории операций. Если в коробку K-4 купили 10 штук, потом продали 3, потом списали 1 — содержимое = 10 - 3 - 1 = 6 штук. Это один SQL-запрос через view.

Почему так: единая правда, невозможно рассинхронизировать, полная история, достаточная производительность для 15-50 коробок.

### 2.2. Реестр коробок — отдельная таблица boxes

Коробки — полноценные сущности с именем и описанием. Создаются заранее, выбираются из выпадающего списка при операциях. Это исключает опечатки ("К-4" vs "K-4" vs "к4") и позволяет управлять коробками (создавать, закрывать, редактировать описание).

### 2.3. Коробка обязательна для всех новых операций

Начиная с момента внедрения, каждая операция (покупка, продажа, списание, корректировка, возврат, перемещение) обязательно привязана к коробке. Старые данные без коробки остаются как есть — расхождения устраняются при первой инвентаризации.

## 3. Изменения в базе данных

### 3.1. Новая таблица inventory.boxes

Хранит реестр коробок/мест хранения. Поля: уникальное имя (строка до 50 символов, например "K-1", "K-4", "ПОЛКА-3"), описание (необязательный текст, например "Верхняя полка, стеллаж A"), флаг активности (можно "закрыть" коробку, чтобы она не появлялась в выпадающих списках, но исторические данные сохранились), дата создания.

При создании таблицы нужно автоматически заполнить её уникальными значениями `box_number` из уже существующих операций — чтобы исторические коробки сразу попали в реестр.

### 3.2. Новая SQL-view inventory.box_contents

Вычисляемое представление, которое группирует операции по коробке и SMART-коду и суммирует qty_delta. Показывает только ненулевые остатки. Фильтрует операции с непустым box_number.

### 3.3. Новое поле linked_movement_id в таблице movements

Целочисленное необязательное поле, ссылающееся на другую запись в той же таблице movements. Используется для связки пары записей при перемещении: запись "убрали из K-4" ссылается на запись "положили в K-7" и наоборот. Это позволяет в истории показывать перемещение как единую операцию.

### 3.4. Новый тип операции transfer

Добавить "transfer" (перемещение) в список допустимых значений поля reason. Перемещение — это две записи в одной транзакции: одна с отрицательным qty_delta (забрали из коробки-источника) и одна с положительным qty_delta (положили в коробку-назначение). Общий остаток товара не меняется.

### 3.5. Новый индекс по box_number

Индекс на movements(box_number) для быстрого вычисления содержимого коробок.

## 4. Изменения в API (Python backend)

### 4.1. Новые эндпоинты для управления коробками

**Получить список коробок.** Возвращает все коробки с суммарным количеством товаров и штук в каждой. Для каждой коробки: имя, описание, количество уникальных SMART-позиций, общее количество штук, дата последней операции, флаг активности. Сортировка по имени.

**Получить содержимое конкретной коробки.** Принимает имя коробки. Возвращает: информацию о коробке (имя, описание) и список товаров внутри — для каждого SMART-кода: количество, обогащённая информация из SMART-кэша (артикулы, название, бренд). Также возвращает историю последних операций, связанных с этой коробкой.

**Создать коробку.** Принимает имя и описание. Проверяет уникальность имени. Возвращает созданную коробку.

**Обновить коробку.** Позволяет изменить описание или закрыть/открыть коробку (is_active). При попытке закрыть коробку с непустым содержимым — предупреждение (но не блокировка).

**Перемещение между коробками.** Принимает: SMART-код, количество, коробку-источник, коробку-назначение. Проверяет, что в коробке-источнике достаточно этого товара. Создаёт две записи в movements в одной SERIALIZABLE транзакции: одну с отрицательным qty_delta для источника, одну с положительным для назначения. Обе записи связаны через linked_movement_id. Reason = "transfer".

### 4.2. Изменения в существующих эндпоинтах

**Создание движения (POST /api/movements).** Валидация: box_number обязателен для типов purchase, writeoff, adjust. Значение box_number должно существовать в таблице boxes и быть активным. Для transfer — используется отдельный эндпоинт.

**Создание заказа (POST /api/orders).** Каждая позиция заказа теперь принимает дополнительное поле box_number. При создании sale-движений в createOrder box_number записывается в movements. Валидация: проверяется не только общий остаток товара, но и остаток этого товара в указанной коробке.

**Создание возврата (POST /api/orders/:id/returns).** Каждая возвращаемая позиция принимает box_number — в какую коробку положить возвращённый товар. Записывается в return-движение.

**Получение остатков (GET /api/stock).** Добавить в ответ информацию о распределении по коробкам для каждого SMART: список пар (box_number, qty). Это позволит на странице остатков видеть, в каких коробках лежит товар.

**Получение деталей товара (GET /api/stock/:smart).** Добавить секцию "распределение по коробкам": для данного SMART показать все коробки, в которых он есть, с количеством в каждой.

**Получение причин (GET /api/reasons).** Добавить "transfer" в список причин с названием "Перемещение".

**Получение списка движений (GET /api/movements).** Убедиться, что box_number возвращается в ответе (уже возвращается). Добавить возможность фильтрации по box_number через query-параметр.

**Обновление движения (PATCH /api/movements/:id).** Box_number уже можно обновлять для покупок. Валидация: значение должно существовать в таблице boxes.

**Массовый импорт (POST /api/bulk-import).** Для строк с reason=purchase — box_number обязателен. Значение должно существовать в таблице boxes. Если коробки нет — информативная ошибка.

### 4.3. Получение коробок, в которых есть конкретный товар

Новый эндпоинт или параметр: по SMART-коду получить список коробок с количеством этого товара в каждой. Используется при создании заказов — чтобы показать пользователю "этот товар есть в K-4 (6 шт.) и K-7 (2 шт.)".

## 5. Изменения во фронтенде

### 5.1. Новый компонент: BoxSelector

Переиспользуемый компонент для выбора коробки. Выпадающий список с поиском (Combobox-паттерн, аналогично SmartSearch, но для коробок). Показывает: имя коробки, описание, количество штук внутри. Только активные коробки. Свойства: onSelect (callback), value (текущее значение), placeholder, disabled, required.

Существуют два режима работы:
- **Общий** (для покупок, корректировок): показывает все активные коробки.
- **Для конкретного товара** (для продаж, списаний): принимает SMART-код, показывает только коробки, в которых есть этот товар, с указанием доступного количества. Остальные коробки скрыты или показаны серым с пометкой "(нет товара)".

### 5.2. Новая страница: Список коробок (/boxes)

Пункт "Коробки" в сайдбаре (иконка Box или Package из Lucide React), между "Остатки" и "История движений".

Содержимое страницы: таблица всех коробок. Столбцы: имя коробки, описание, количество уникальных позиций (SMART-кодов), общее количество штук, дата последней активности. Строки кликабельны — переход на страницу детальной коробки.

Фильтр по имени коробки. Кнопка "Создать коробку" — открывает модальное окно или inline-форму для ввода имени и описания.

Особая строка в конце таблицы: "Товары без коробки" — показывает количество SMART-позиций и штук, которые числятся на складе, но не привязаны ни к одной коробке (из-за исторических данных). Кликабельна — показывает список этих товаров.

### 5.3. Новая страница: Содержимое коробки (/boxes/:name)

Заголовок: имя коробки и описание (редактируемое inline). Кнопки действий: "Переместить", "Инвентаризация", "Редактировать".

Секция "Содержимое": таблица товаров в этой коробке. Столбцы: SMART-код (ссылка на /stock/:smart), артикулы, название, количество. Кнопка "Переместить" напротив каждого товара — открывает модалку/форму перемещения (выбор коробки-назначения и количества).

Секция "История операций": последние N операций, связанных с этой коробкой. Столбцы: дата, SMART, количество (с цветом +/-), причина (бейдж), примечание. Для перемещений — показывать "→ K-7" или "← K-1".

### 5.4. Функция инвентаризации на странице коробки

Кнопка "Инвентаризация" на странице коробки открывает специальный режим. Система показывает таблицу: SMART-код, ожидаемое количество (из view), поле ввода для фактического количества, вычисленная разница, статус (ок/расхождение).

Пользователь физически пересчитывает коробку и вводит фактические числа. Для позиций с расхождением система подсвечивает их (красный/жёлтый). Кнопка "Применить корректировки" создаёт adjust-операции для каждого расхождения: если ожидалось 6, а по факту 4 — создаётся adjust с qty_delta = -2, box_number = эта коробка, note = "Инвентаризация: расхождение -2".

Также должна быть возможность добавить товар, которого нет в ожидаемом списке (нашли в коробке неучтённый товар) — это adjust с положительным qty_delta.

### 5.5. Изменения на странице "Добавить движение" (/movement)

Поле "Номер коробки" заменяется компонентом BoxSelector. Для покупок — общий режим (все активные коробки). Для списаний — режим "для товара" (только коробки, где есть выбранный SMART). Для корректировок — общий режим.

Новая причина "Перемещение" в выпадающем списке причин. При выборе "Перемещение" форма перестраивается: появляются два поля BoxSelector ("Из коробки" и "В коробку") вместо одного, а поля цен скрываются. Количество положительное (сколько штук переместить). Примечание опционально.

### 5.6. Изменения на странице заказов (/orders — sold-items.tsx)

Каждая позиция заказа получает дополнительное поле BoxSelector в режиме "для товара". После выбора SMART-кода список коробок фильтруется — показываются только коробки, содержащие этот товар, с указанием доступного количества. Нельзя выбрать коробку, в которой товара нет. Нельзя указать количество больше, чем есть в выбранной коробке.

Если нужно взять товар из нескольких коробок (например, 6 из K-4 и 2 из K-7), пользователь создаёт две отдельные позиции с одним SMART-кодом, но разными коробками.

### 5.7. Изменения на странице деталей заказа (/orders/:id — order-details.tsx)

В таблице позиций заказа добавить столбец "Коробка" — показывает, из какой коробки был взят товар.

При оформлении возврата: каждая возвращаемая позиция получает BoxSelector — в какую коробку положить возвращённый товар. Система подсказывает коробку, из которой товар был продан, но позволяет выбрать другую.

### 5.8. Изменения на странице деталей товара (/stock/:smart — stock-details.tsx)

Новая секция "Распределение по коробкам" между заголовком и таблицей покупок. Показывает таблицу: коробка, количество штук, кнопка "Переместить". Строка "Всего" и строка "Без коробки" (если есть нераспределённый остаток). Ссылки на коробки — клик переходит на /boxes/:name.

### 5.9. Изменения на странице истории движений (/history — movement-history.tsx)

Добавить столбец "Коробка" в таблицу. Для перемещений показывать стрелку: "K-4 → K-7". Добавить фильтр по коробке (dropdown со списком коробок). Обогащать данные: для операций с box_number показывать бейдж с именем коробки.

### 5.10. Изменения на странице массовой загрузки (/import — bulk-import.tsx)

В шаблоне Excel: пометить box_number как обязательное поле для покупок. В валидации загружаемых данных: проверять, что box_number присутствует для reason=purchase, и что указанная коробка существует в реестре.

## 6. Правила валидации

### 6.1. Обязательность box_number по типам операций

Покупка (purchase): коробка обязательна. Товар кладётся в конкретную коробку.

Продажа (sale): коробка обязательна. Товар берётся из конкретной коробки. Проверяется, что в этой коробке достаточно товара.

Списание (writeoff): коробка обязательна. Товар убирается из конкретной коробки. Проверяется, что в этой коробке достаточно товара.

Корректировка (adjust): коробка обязательна. Корректируется содержимое конкретной коробки. При отрицательном qty_delta проверяется, что в коробке достаточно товара.

Возврат (return): коробка обязательна. Возвращённый товар кладётся в указанную коробку.

Перемещение (transfer): две коробки обязательны (источник и назначение). Проверяется, что в коробке-источнике достаточно товара. Источник и назначение не должны совпадать.

### 6.2. Валидация существования коробки

Значение box_number должно существовать в таблице boxes. Коробка должна быть активной (is_active = true). Если коробка не найдена или неактивна — информативная ошибка.

### 6.3. Валидация остатка в коробке

Для операций, уменьшающих содержимое коробки (продажа, списание, отрицательная корректировка, перемещение из коробки): проверять, что в указанной коробке достаточно этого товара. Проверка выполняется внутри SERIALIZABLE транзакции — так же, как сейчас проверяется общий остаток.

Сообщение об ошибке: "В коробке {name} только {available} шт. {smart}. Запрошено: {requested}."

## 7. Перемещение между коробками — детали

Перемещение — это атомарная операция, создающая две записи в movements в одной транзакции.

Первая запись: smart = выбранный товар, qty_delta = отрицательное число (минус количество), reason = "transfer", box_number = коробка-источник, note = "→ {назначение}", linked_movement_id = id второй записи.

Вторая запись: smart = тот же товар, qty_delta = положительное число (плюс количество), reason = "transfer", box_number = коробка-назначение, note = "← {источник}", linked_movement_id = id первой записи.

Общий остаток товара не меняется: qty_delta первой + qty_delta второй = 0. Но содержимое коробок обновляется.

Перед созданием записей проверяется: в коробке-источнике достаточно товара, обе коробки существуют и активны, коробки не совпадают.

## 8. Обработка исторических данных

### 8.1. Проблема

Существующие покупки уже имеют box_number. Существующие продажи, списания и корректировки — не имеют. Из-за этого view box_contents покажет завышенные числа (покупки учтены, а продажи — нет).

### 8.2. Решение

При развёртывании системы происходит следующее:

Из уникальных значений box_number в таблице movements автоматически создаются записи в таблице boxes. Это гарантирует, что все исторические коробки попадут в реестр.

View box_contents создаётся и начинает показывать содержимое. Для коробок, из которых продавались товары без привязки к коробке, числа будут завышены.

Пользователь проводит первую инвентаризацию каждой коробки через интерфейс инвентаризации. Вводит фактические количества, система создаёт корректировки для расхождений. После этого данные становятся точными.

В дальнейшем все операции привязаны к коробкам, и содержимое всегда актуально.

## 9. Крайние случаи

### 9.1. Попытка продать больше, чем есть в коробке

В K-4 лежит 3 шт. smart_10809. Заказ на 5 шт. из K-4. Система блокирует: "В коробке K-4 только 3 шт." Пользователь должен создать две позиции: 3 из K-4 и 2 из K-7 (если там есть).

### 9.2. Закрытие коробки с содержимым

Пользователь хочет закрыть (деактивировать) коробку K-4, но в ней ещё есть товар. Система показывает предупреждение: "В коробке K-4 ещё 23 штуки товара. Сначала переместите товар в другие коробки." Закрытие разрешается, но с предупреждением — пользователь может осознанно закрыть коробку (например, все товары уже физически перемещены, но не отражены в системе).

### 9.3. Товары без коробки

Товары, которые числятся на складе (stock > 0), но не привязаны ни к одной коробке. Это возникает из-за исторических данных. На странице списка коробок показывается отдельная строка "Товары без коробки" с количеством. При клике — список товаров. Каждому можно назначить коробку через корректировку.

### 9.4. Одна закупка — несколько коробок

Купил 10 штук, 6 кладёт в K-4, 4 в K-7. Создаёт две отдельные покупки с одинаковым SMART и ценой, но разными коробками и количествами. Система это поддерживает без изменений.

### 9.5. Один SMART в одной коробке из разных закупок

Купил 3 по 400 рублей в K-4, потом ещё 2 по 500 рублей в K-4. В box_contents отображается 5 штук в K-4. Это нормально — view суммирует.

### 9.6. Перемещение при SERIALIZABLE-конфликте

Два пользователя одновременно перемещают из одной коробки. Транзакция использует SERIALIZABLE уровень изоляции. При конфликте — retry с exponential backoff (как в текущей реализации createMovement).

## 10. Порядок реализации (три этапа)

### Этап 1: Фундамент

Таблица boxes в БД с автозаполнением из исторических данных. View box_contents. Поле linked_movement_id в movements. Тип операции transfer в справочнике причин. Индекс по box_number. API эндпоинты для управления коробками (CRUD, содержимое, перемещение). Новая страница "Список коробок". Новая страница "Содержимое коробки" с историей.

Результат первого этапа: можно видеть содержимое коробок, создавать/редактировать коробки, просматривать историю операций по коробке.

### Этап 2: Интеграция с операциями

Компонент BoxSelector. Замена текстового поля на BoxSelector в форме добавления движения. Добавление причины "Перемещение" в форму добавления движения с двумя полями BoxSelector. Интеграция с заказами: BoxSelector для каждой позиции заказа. Интеграция с возвратами: BoxSelector для каждой возвращаемой позиции. Валидация остатка в коробке при продажах, списаниях, корректировках. Обновление страницы деталей товара (секция распределения по коробкам). Обновление страницы истории движений (столбец и фильтр по коробке). Обновление массового импорта (обязательность box_number для покупок).

Результат второго этапа: полноценный учёт содержимого коробок, все операции привязаны к коробкам.

### Этап 3: Инвентаризация

Форма инвентаризации на странице коробки: ожидаемое vs. фактическое. Автоматическое создание корректировок для расхождений. Отображение "товаров без коробки" с возможностью распределения. Первичная инвентаризация всех коробок для устранения расхождений исторических данных.

Результат третьего этапа: перепроверка и корректировка содержимого коробок в любой момент.
