# Архитектура хранения данных EventHorizon

## Общая схема

Система использует **две отдельные PostgreSQL базы данных** + **in-memory кэш** на сервере.

```
┌─────────────┐         ┌──────────────────┐         ┌─────────────────┐
│  Parts DB   │────────▶│  Сервер (Node.js) │◀───────▶│  Inventory DB   │
│ (read-only) │  старт  │                  │  r/w    │  (read-write)   │
└─────────────┘         │  ┌────────────┐  │         └─────────────────┘
                        │  │ SMART-кэш  │  │
                        │  │ (in-memory)│  │
                        │  └────────────┘  │
                        └──────────────────┘
```

---

## 1. Parts DB (SMART-справочник)

**Подключение:** переменные окружения `PARTS_DB_*`
**Режим:** только чтение, периодическое обновление каждые 10 минут

### Таблица `public.smart`

Содержит каталог всех запчастей. Колонки в БД имеют русские имена.

| Колонка в БД        | Маппинг в коде | Тип данных  | Описание                          |
|----------------------|----------------|-------------|-----------------------------------|
| `smart`              | `smart`        | string      | Уникальный SMART-код запчасти     |
| `артикул`            | `articles`     | string[]    | Массив артикулов                  |
| `наименование`       | `name`         | string/null | Название запчасти                 |
| `бренд`              | `brand`        | string[]    | Массив брендов                    |
| `коннект_бренд`      | `description`  | string[]    | Массив описаний (коннект-бренды)  |

**Когда читается:** при старте сервера и далее каждые 10 минут. Все строки загружаются в оперативную память (SMART-кэш). При обновлении старый кэш атомарно подменяется новым. Если обновление не удалось — сервер продолжает работать со старым кэшем.

---

## 2. SMART-кэш (оперативная память сервера)

**Файл:** `server/smart-cache.ts`

При старте (и далее каждые 10 минут) вся таблица `public.smart` загружается в `Map<string, SmartInternal>`.

Для каждой записи дополнительно хранятся нормализованные значения:
- `normalizedSmart` — SMART-код после нормализации (убраны разделители, приведён к нижнему регистру)
- `normalizedArticles` — массив нормализованных артикулов

### Что умеет кэш

| Метод       | Что делает                                                        |
|-------------|-------------------------------------------------------------------|
| `getBySmart` | Мгновенный поиск записи по точному SMART-коду                    |
| `search`     | Fuzzy-поиск по нормализованному запросу с ранжированием (score)   |

### Приоритет ранжирования при поиске

| Score | Условие                             |
|-------|--------------------------------------|
| 100   | Точное совпадение артикула           |
| 90    | Артикул начинается с запроса         |
| 80    | Артикул содержит запрос              |
| 70    | Точное совпадение SMART              |
| 60    | SMART начинается с запроса           |
| 50    | SMART содержит запрос                |

Максимум результатов по умолчанию: 50.

## 3. Inventory DB (складской учёт)

**Подключение:** переменные окружения `INVENTORY_DB_*`
**Режим:** чтение и запись
**Схема:** `inventory`

### 3.1. Таблица `inventory.reasons`

Справочник типов операций. **Фиксированный набор**, перезаписывается при каждом старте.

| code       | title          |
|------------|----------------|
| `purchase` | Покупка        |
| `sale`     | Продажа        |
| `return`   | Возврат        |
| `writeoff` | Списание       |
| `adjust`   | Корректировка  |

Любые "лишние" коды удаляются при старте. Таблица movements **не имеет FK** на reasons — это просто справочник для UI.

### 3.2. Таблица `inventory.shipping_methods`

Справочник способов доставки.

| Колонка      | Тип       | Описание                     |
|--------------|-----------|------------------------------|
| `id`         | SERIAL PK | Автоинкремент                |
| `name`       | TEXT      | Название способа доставки    |
| `created_at` | TIMESTAMP | Дата создания                |

**Дефолтные записи** (вставляются если таблица пуста при старте):
- Почта России
- Яндекс
- СДЭК
- Авито доставка

Пользователь может добавлять и удалять способы доставки через API.

### 3.3. Таблица `inventory.movements` (ЯДРО СИСТЕМЫ)

Каждая строка — одна складская операция. **Это единственный источник истины** для всех остатков, аналитики и истории.

| Колонка              | Тип           | Описание                                          |
|----------------------|---------------|---------------------------------------------------|
| `id`                 | SERIAL PK     | Уникальный ID операции                            |
| `smart`              | VARCHAR       | SMART-код товара (НЕ артикул!)                    |
| `qty_delta`          | INTEGER       | Изменение количества (+ приход, - расход)         |
| `reason`             | VARCHAR       | Тип операции (purchase/sale/return/writeoff/adjust)|
| `note`               | TEXT          | Примечание (nullable)                             |
| `purchase_price`     | NUMERIC(10,2) | Цена закупки (nullable)                           |
| `sale_price`         | NUMERIC(10,2) | Цена продажи (nullable)                           |
| `delivery_price`     | NUMERIC(10,2) | Стоимость доставки (nullable)                     |
| `box_number`         | VARCHAR(50)   | Номер коробки (nullable)                          |
| `track_number`       | TEXT          | Трек-номер отправления (nullable)                 |
| `shipping_method_id` | INTEGER       | ID способа доставки (nullable)                    |
| `sale_status`        | VARCHAR(50)   | Статус продажи (nullable)                         |
| `created_at`         | TIMESTAMP     | Дата/время операции (NOW() при вставке)           |

**Индексы:**
- `movements_smart_idx` — по SMART-коду
- `movements_reason_idx` — по типу операции
- `movements_created_at_idx` — по дате (DESC)
- `movements_sale_status_idx` — по статусу продажи

### 3.4. VIEW `inventory.stock`

**Не хранит данные** — вычисляет на лету из movements.

```sql
SELECT smart, SUM(qty_delta) as total_qty
FROM inventory.movements
GROUP BY smart
HAVING SUM(qty_delta) > 0
```

Показывает только товары с **положительным** остатком. Товары с нулевым остатком исчезают из этого VIEW, но их история навсегда остаётся в movements.

## 4. Какие данные записываются при каждом типе операции

### 4.1. Покупка (purchase)

| Поле              | Значение                           |
|-------------------|------------------------------------|
| `smart`           | SMART-код (обязательно)            |
| `qty_delta`       | **положительное** число            |
| `reason`          | `"purchase"`                       |
| `purchase_price`  | обязательно, числовая строка       |
| `box_number`      | обязательно                        |
| `note`            | опционально                        |
| `sale_price`      | **всегда null**                    |
| `delivery_price`  | **всегда null**                    |
| `track_number`    | **всегда null**                    |
| `shipping_method_id` | **всегда null**                 |
| `sale_status`     | **всегда null**                    |

### 4.2. Продажа (sale)

| Поле              | Значение                           |
|-------------------|------------------------------------|
| `smart`           | SMART-код (обязательно)            |
| `qty_delta`       | **отрицательное** число            |
| `reason`          | `"sale"`                           |
| `sale_price`      | обязательно, числовая строка       |
| `delivery_price`  | обязательно, числовая строка       |
| `shipping_method_id` | обязательно, положительное число|
| `track_number`    | опционально                        |
| `note`            | опционально                        |
| `sale_status`     | **сервер ставит `"awaiting_shipment"` автоматически** |
| `purchase_price`  | **всегда null**                    |
| `box_number`      | **всегда null**                    |

**Проверка перед вставкой:** текущий остаток >= запрашиваемое количество.

### 4.3. Возврат (return)

| Поле              | Значение                           |
|-------------------|------------------------------------|
| `smart`           | SMART-код из оригинальной продажи  |
| `qty_delta`       | **положительное** (= abs от продажи) |
| `reason`          | `"return"`                         |
| `note`            | обязательно, формат: `"Возврат продажи #<id>"` |
| все остальные     | **всегда null**                    |

**Особенности:**
- Создаётся **только** через эндпоинт `POST /api/movements/:id/return`
- Нельзя создать через общую форму или массовый импорт
- Защита от повторного возврата: если в movements уже есть return с таким же note — ошибка

### 4.4. Списание (writeoff)

| Поле              | Значение                           |
|-------------------|------------------------------------|
| `smart`           | SMART-код (обязательно)            |
| `qty_delta`       | **отрицательное** число            |
| `reason`          | `"writeoff"`                       |
| `note`            | опционально                        |
| все остальные     | **всегда null**                    |

**Проверка перед вставкой:** текущий остаток >= запрашиваемое количество.

### 4.5. Корректировка (adjust)

| Поле              | Значение                                |
|-------------------|------------------------------------------|
| `smart`           | SMART-код (обязательно)                  |
| `qty_delta`       | любое ненулевое число (+ или -)          |
| `reason`          | `"adjust"`                               |
| `note`            | **обязательно**                          |
| `purchase_price`  | опционально (если указано — валидируется как число) |
| все остальные     | **всегда null**                          |

**Проверка перед вставкой:** если qty_delta < 0, текущий остаток >= запрашиваемое количество.

## 5. Сводная таблица: что заполняется при каждом типе

```
Поле                 purchase  sale      return  writeoff  adjust
─────────────────────────────────────────────────────────────────
smart                ✓ обяз.   ✓ обяз.   ✓ авто  ✓ обяз.   ✓ обяз.
qty_delta            + обяз.   - обяз.   + авто  - обяз.   ± обяз.
note                 опц.      опц.      обяз.   опц.      обяз.
purchase_price       обяз.     null      null    null      опц.
sale_price           null      обяз.     null    null      null
delivery_price       null      обяз.     null    null      null
box_number           обяз.     null      null    null      null
track_number         null      опц.      null    null      null
shipping_method_id   null      обяз.     null    null      null
sale_status          null      авто*     null    null      null
```

`авто*` = сервер ставит `"awaiting_shipment"` при создании.

## 6. Потоки данных: откуда что читается

### Поиск артикулов (`GET /api/articles/search`)
1. Поиск по **SMART-кэшу** (in-memory)
2. Batch-запрос остатков из **VIEW `inventory.stock`** по найденным SMART-кодам
3. Объединение на сервере → отдача клиенту

### Уровни запасов (`GET /api/stock`)
1. Чтение из **VIEW `inventory.stock`**
2. Обогащение данными из **SMART-кэша** (имя, бренд, артикулы)

### Детали по SMART (`GET /api/stock/:smart`)
1. SQL-запрос `COUNT(*) + SUM(qty_delta)` из **таблицы movements** по SMART-коду
2. Если операций по этому SMART не было → 404
3. Если были, но остаток = 0 → отдаёт `totalQty: 0`
4. Обогащение из **SMART-кэша**

### История операций (`GET /api/movements`)
1. `SELECT * FROM inventory.movements ORDER BY created_at DESC`
2. Каждая строка обогащается данными из **SMART-кэша**

### Аналитика продаж (`GET /api/stock/:smart/sales`)
1. Параллельно: продажи + покупки по SMART из **таблицы movements**
2. Расчёт средневзвешенной цены закупки на сервере
3. Расчёт прибыли, маржи, дней до продажи — всё в JS на сервере

### Проданные до нуля (`GET /api/sold-out`)
1. SQL с двумя CTE из **таблицы movements**: агрегация продаж + текущий остаток
2. Фильтр: `current_stock = 0`
3. Обогащение из **SMART-кэша**

### Рейтинг товаров (`GET /api/top-parts`)
1. SQL с тремя CTE из **таблицы movements**: средняя закупка, метрики продаж, текущий остаток
2. Сортировка в JS по выбранному режиму (profit/sales/combined)
3. Обогащение из **SMART-кэша**

### Дашборд (`GET /api/dashboard/stats`)
1. Один SQL-запрос с четырьмя CTE из **таблицы movements** и **VIEW stock**:
   - Количество уникальных SMART на складе
   - Общее количество единиц
   - Операций за сегодня
   - Продаж за сегодня

## 7. Транзакционные гарантии

### SERIALIZABLE изоляция
Все операции записи (создание и редактирование movement) выполняются в транзакциях с уровнем `SERIALIZABLE`. Это самый строгий уровень — PostgreSQL гарантирует, что параллельные транзакции дадут тот же результат, что и последовательное выполнение.

### Retry при конфликтах
Если PostgreSQL обнаруживает конфликт сериализации (код ошибки `40001`), сервер автоматически повторяет операцию до **3 раз** с экспоненциальной задержкой (100мс → 200мс → 400мс).

### Проверка остатка
Для операций, уменьшающих запас (sale, writeoff, отрицательный adjust), внутри той же транзакции проверяется `SUM(qty_delta) >= запрашиваемое_количество`. Благодаря SERIALIZABLE это атомарно и race-condition невозможен.

## 8. Инициализация схемы при старте

Файл `server/inventory-schema.ts` — выполняется один раз при каждом запуске сервера.

Порядок:
1. `CREATE SCHEMA IF NOT EXISTS inventory`
2. `CREATE TABLE IF NOT EXISTS inventory.reasons` → UPSERT 5 записей → удаление лишних
3. `CREATE TABLE IF NOT EXISTS inventory.shipping_methods` → вставка 4 дефолтных (если пусто)
4. `CREATE TABLE IF NOT EXISTS inventory.movements` (базовые колонки)
5. `DROP COLUMN IF EXISTS article` (по спецификации — артикул не хранится)
6. `ADD COLUMN IF NOT EXISTS` для 7 расширенных колонок (идемпотентно)
7. `CREATE OR REPLACE VIEW inventory.stock`
8. Создание 4 индексов (`IF NOT EXISTS`)

Всё это — в одной транзакции. Если что-то падает — ROLLBACK.

## 9. Подключения к БД

Оба пула создаются из переменных окружения:

| Переменная          | Parts DB          | Inventory DB          |
|---------------------|-------------------|-----------------------|
| Хост                | `PARTS_DB_HOST`   | `INVENTORY_DB_HOST`   |
| Порт                | `PARTS_DB_PORT`   | `INVENTORY_DB_PORT`   |
| Имя базы            | `PARTS_DB_NAME`   | `INVENTORY_DB_NAME`   |
| Пользователь        | `PARTS_DB_USER`   | `INVENTORY_DB_USER`   |
| Пароль              | `PARTS_DB_PASSWORD`| `INVENTORY_DB_PASSWORD`|
| SSL                 | `PARTS_DB_SSL`    | `INVENTORY_DB_SSL`    |

Параметры пула (одинаковые для обоих):
- `max: 10` соединений
- `connectionTimeoutMillis: 20_000` (20 сек)
- `idleTimeoutMillis: 30_000` (30 сек)
