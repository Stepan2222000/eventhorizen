# Item-based inventory (экземпляры запчастей) — как реализовано сейчас (as-is)

Дата фиксации: 2026-02-10  
Проект: EventHorizon / SMART инвентаризация

Этот документ описывает **текущее фактическое поведение** системы учета (backend + frontend) после внедрения item-based подхода, чтобы было понятно:

- где “истина” по остаткам;
- как выполняются покупки/продажи/перемещения/возвраты;
- какие инварианты уже гарантируются;
- какие пункты из `lab/item-system-spec.md` **еще не реализованы** (осознанно, чтобы не ломать инварианты).

---

## 1) Главный принцип (как сейчас)

### 1.1. Источник истины = `inventory.items`

Текущее складское состояние **считается из физических экземпляров**:

- общий остаток по SMART = `COUNT(items WHERE smart=X AND state='in_stock')`
- остаток по SMART в коробке = `COUNT(items WHERE smart=X AND state='in_stock' AND box_number=B)`

Таблица `inventory.movements` сохраняется как журнал операций/истории, но **не является источником истины** для остатков.

### 1.2. История и трассировка = `movement_items`

Для каждой операции фиксируется список конкретных экземпляров:

- `inventory.movement_items (movement_id, item_id)` связывает движение и items.
- Это позволяет открыть движение и увидеть, **какие конкретно экземпляры** оно затронуло.

---

## 2) Модель данных (как сейчас)

### 2.1. Таблицы

- `inventory.items`
  - `id BIGSERIAL` (уникальный идентификатор экземпляра)
  - `smart VARCHAR NOT NULL`
  - `state` in: `in_stock | sold | written_off`
  - `box_number` (только если `state='in_stock'`)
  - `note`
  - ссылки на “последние движения”: `purchase_movement_id`, `sold_movement_id`, `written_off_movement_id`, `last_movement_id`
  - `created_at`, `updated_at`

- `inventory.movements`
  - журнал операций (purchase/sale/return/writeoff/adjust/transfer)
  - расширенные поля уже существующей системы (цены, доставка, order/shipment/return связи, linked_movement_id для transfer)

- `inventory.movement_items`
  - связь “движение → конкретные экземпляры”

- `inventory.item_media`
  - метаданные медиа на уровне item (mime, sha256, размер, kind=photo|video, soft-delete `deleted_at`)

- `inventory.item_media_chunks`
  - чанки `BYTEA` для хранения бинарных данных медиа в Postgres

### 2.2. Представления (VIEW)

- `inventory.stock` теперь считает остатки по SMART из `inventory.items (state='in_stock')`
- `inventory.box_contents` теперь считает содержимое коробок из `inventory.items (state='in_stock')`

## 3) ItemCode (человекочитаемый код экземпляра)

Сейчас `item_code` **не хранится в БД отдельным полем**.

UI/API показывают `itemCode`, который **детерминированно вычисляется из `items.id`**:

- формат: `EH-000001`, `EH-000002`, ...
- уникален, не переиспользуется
- подходит для поиска и наклеек

---

## 4) Инварианты (что уже гарантируется)

### 4.1. Инварианты на уровне БД (CHECK/FK)

В `inventory.items` есть CHECK-и:

- `state` только из допустимых значений (`in_stock`, `sold`, `written_off`)
- если `state='in_stock'`, то `box_number` обязателен и не пустой
- если `state!='in_stock'`, то `box_number` должен быть `NULL`/пустой
- если `state='sold'`, то `sold_movement_id` обязателен
- если `state='written_off'`, то `written_off_movement_id` обязателен

Есть FK:

- `items.box_number -> boxes(name)`
- `items.*_movement_id -> movements(id)`
- `movement_items.movement_id -> movements(id)` (CASCADE)
- `movement_items.item_id -> items(id)` (CASCADE)

### 4.2. Инварианты на уровне приложения

- Нельзя использовать неактивную (закрытую) коробку как `boxNumber` для операций (backend canonicalize + validate active).
- Нельзя закрыть коробку, если в ней есть `in_stock` items (проверка через `box_contents`).
- Все операции с изменением остатков выполняются **в транзакциях SERIALIZABLE** (в т.ч. с ретраями в некоторых местах), чтобы не допустить гонок.

## 5) Операции (как именно меняется склад)

Важно: “операция” сейчас хранится как строка в `inventory.movements`, а “какие items затронуты” хранится в `movement_items`.

### 5.1. Purchase / Adjust(+)

API `POST /api/movements` с `reason=purchase` или `reason=adjust` и `qtyDelta>0`:

- создается движение `movements`
- создаются `qty` новых строк в `items`:
  - `state='in_stock'`
  - `box_number=коробка`
  - `purchase_movement_id = movement_id`
  - `last_movement_id = movement_id`
- создаются связи `movement_items` для всех созданных item_id

### 5.2. Writeoff / Adjust(-)

API `POST /api/movements` с `reason=writeoff` (qtyDelta<0) или `reason=adjust` (qtyDelta<0):

- выбираются конкретные items из указанной коробки (FIFO по `id`)
- items переводятся в `written_off`, `box_number=NULL`
- пишется `written_off_movement_id` и `last_movement_id`
- создаются связи `movement_items` для списанных item_id

### 5.3. Transfer (между коробками)

API `POST /api/boxes/transfer`:

- создаются **две** строки в `movements` (как раньше):
  - `transfer -qty` для `fromBox`
  - `transfer +qty` для `toBox`
  - они связаны через `linked_movement_id`
- выбираются конкретные items из `fromBox` (FIFO по `id`)
- у выбранных items меняется `box_number=toBox`, `last_movement_id = (toMovementId)`
- эти же item_id привязываются через `movement_items` **к обеим строкам transfer**

Примечание: ручной выбор конкретных item_id для transfer **пока не реализован** (только FIFO).

### 5.4. Sale через заказы (основной путь)

Создание заказа (страница заказов) создает sale-движения и “снимает” экземпляры со склада.

Особенность: при продаже можно:

- указать коробку, из которой продаем,
- (опционально) выбрать **конкретные экземпляры** (`itemIds`) из этой коробки.

В результате:

- создается sale движение `movements` c `qtyDelta=-qty`
- выбранные items переводятся в:
  - `state='sold'`
  - `box_number=NULL`
  - `sold_movement_id = sale_movement_id`
  - `last_movement_id = sale_movement_id`
- создаются `movement_items` для проданных item_id

### 5.5. Sale без заказа (через ручной ввод движения)

Страница “Добавить движение” позволяет создать `reason=sale` через `POST /api/movements`.

Сейчас это работает так:

- выбор конкретных экземпляров **не поддерживается** (только FIFO из коробки)
- но трассировка сохраняется: sale движение будет связано с item_id через `movement_items`

### 5.6. Return (возврат) через заказ (основной путь)

Возврат делается со страницы заказа (секция “Оформить возврат/корректировку”).

Текущее правило: для возврата **обязательно** передать `itemIds`, чтобы вернуть “ту же самую штуку”.

Проверки на backend:

- каждый itemId существует
- `item.smart` совпадает со SMART позиции заказа
- `item.state == 'sold'`
- `item.sold_movement_id` совпадает с sale-движением нужной позиции заказа

После этого:

- создается `return` движение
- items переводятся обратно в:
  - `state='in_stock'`
  - `box_number=выбранная коробка`
  - `sold_movement_id=NULL`
  - `last_movement_id=return_movement_id`
- создаются `movement_items` для return движения

### 5.7. Return (ручной ввод движения)

Через `POST /api/movements` с `reason=return` сейчас технически можно создать возврат, но он **не возвращает те же проданные items** (так как нет itemIds), а создает новые items как при покупке.

Это поведение **не соответствует** цели “возвращать ту же самую штуку” и должно считаться legacy/временным.

---

## 6) Коробки (активность/закрытие)

- Любая операция, требующая коробку (`purchase/adjust/writeoff/sale/return/transfer`), принимает только **активную** коробку.
- `PATCH /api/boxes/:name` с `isActive=false` запрещен, если в коробке есть items на складе (через `box_contents`).
- Закрытая коробка не должна содержать `in_stock` items (гарантируется запретом закрытия не пустой коробки).

---

## 7) Медиа на уровне item (PostgreSQL bytes)

### 7.1. Хранение

Загрузка: `POST /api/items/{itemId}/media` (multipart):

- создается запись `item_media` (метаданные)
- файл читается чанками и сохраняется в `item_media_chunks`
- вычисляется `sha256`, сохраняется `size_bytes`

Удаление: `DELETE /api/item-media/{mediaId}`:

- soft-delete (`deleted_at=NOW()`), чанки остаются связаны FK и исчезнут только при полном удалении media записи (в системе не используется).

### 7.2. Отдача и воспроизведение видео (Range)

Просмотр/скачивание: `GET /api/item-media/{mediaId}`

- поддерживается `Range: bytes=...` (возвращает `206 Partial Content`)
- это нужно для нормального воспроизведения видео в браузере

## 8) UI (что добавлено/изменено)

### 8.1. Новые страницы

- `/items` — список экземпляров (фильтры + поиск по `EH-000123` или по id)
- `/items/:id` — карточка экземпляра:
  - заметка
  - медиа (загрузка/просмотр/видео)
  - движения, которые касались этого экземпляра

### 8.2. Заказы (продажа/возврат)

- при продаже в заказе можно выбрать коробку и (опционально) выбрать конкретные экземпляры
- при возврате требуется выбрать конкретные экземпляры из списка “проданных в этой позиции” (чтобы вернуть именно их)

## 9) Редактирование/удаление движений (как сейчас)

Требование на будущее: редактировать/удалять движения без потери инвариантов через `void/replace`.

Сейчас:

- `PATCH /api/movements/:id` **запрещает** редактирование `qtyDelta` и `boxNumber` (возвращает 400).
- Разрешено редактирование только для покупок: `purchasePrice` и `note`.
- `DELETE /api/movements/:id` **не реализован**.

Причина: прямое “редактирование количества/коробки” или физическое удаление движения без продуманного `void/replace`
может рассинхронизировать журнал (`movements`) и состояние экземпляров (`items`) и привести к “утечкам/пропажам”.

---

## 10) Миграция legacy данных (как сейчас)

При инициализации схемы, если `inventory.items` пустая, а `inventory.movements` не пустая, выполняется одноразовая миграция:

- движения с `box_number` проигрываются в items (создаются/списываются экземпляры, строятся `movement_items`)
- “безкоробочные” (старые) дельты агрегируются по SMART и компенсируются через специальный этап MIGRATION:
  - при положительном net создаются items в активной “служебной” коробке `NO-BOX`
  - при отрицательном net выполняется списание (writeoff) реальных items (где возможно)

Цель миграции: привести систему к состоянию, где остатки из items сходятся с legacy суммами, но при этом честно обозначить “неопределенное место” через `NO-BOX`.

---

## 11) Что еще не сделано (ключевые пробелы относительно спецификации)

- Нет “настоящего” редактирования/удаления движений по правилам `void/replace` (пока только запреты).
- `itemCode` не хранится отдельным полем в БД (только вычисляется из `id`).
- Transfer не поддерживает выбор конкретных экземпляров (только FIFO).
- Ручной `return` через страницу “Добавить движение” не привязан к ранее проданным items (создает новые items) и считается legacy/временным поведением.
- Нет автоматического набора инвариант-тестов (есть только практические сценарии проверки через UI).

---

## 12) Практическая проверка (что прогонялось вручную)

Сценарии, которые проверялись через UI:

- покупка → появление items в коробке → отражение в остатках/коробках
- transfer между коробками → общий остаток не меняется, распределение меняется
- продажа из выбранной коробки с выбором конкретных items → уходит ровно выбранное
- возврат с выбором конкретных items → возвращаются те же экземпляры, снова `in_stock` в выбранной коробке
- запрет закрыть коробку с товаром; закрытие пустой коробки возможно; закрытую нельзя выбрать в операциях
- медиа: загрузка фото/видео, воспроизведение видео (Range/206)
