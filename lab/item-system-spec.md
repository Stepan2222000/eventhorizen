# Система учета экземпляров запчастей (Item-based inventory) — спецификация (черновик)

Дата: 2026-02-10  
Проект: EventHorizon / SMART инвентаризация

Документ фиксирует целевую логику системы так, как мы договорились в обсуждении. Это **описание словами** (без реализации), с упором на:

- отсутствие путаницы и противоречий;
- строгую “зацикленность” учета (все взаимосвязано);
- трассируемость: всегда понятно, что случилось с каждой конкретной запчастью;
- медиа (фото/видео) **на уровне конкретной штуки** (item), хранение **в PostgreSQL** “в байтах”.

---

## 0. Ключевые принятые решения (итог обсуждения)

1. Выбираем вариант **C**: вводим сущность **экземпляра запчасти** (`item`).  
   Один `SMART` = тип/модель запчасти, а `items` = физические штуки этого SMART.
2. При продаже пользователь указывает, **из какой коробки** списываются запчасти.  
   Дополнительно: можно **выбирать конкретные items** из выбранной коробки (ручной выбор).
3. Возврат делается с экрана **отправки (shipment)**: при возврате должна вернуться **та же самая запчасть**, то есть те же item-экземпляры, которые были отправлены/проданы.
4. Коробки:
   - неактивные коробки **нельзя** выбирать/использовать;
   - в неактивных коробках **не может быть** товара (items на складе);
   - закрытие коробки с товаром должно быть **запрещено** (hard-block).
5. Хранение фото/видео: **только на уровне item**, хранить **в PostgreSQL** (байты).
6. Ограничений “по бизнес-правилам” на размер/количество медиа не вводим, но вводим обязательные **технические предохранители**, чтобы система не падала (см. раздел “Медиа”).
7. Запчасти существуют только из справочника SMART (parts DB).  
   Пользователь не добавляет “левые” запчасти вне SMART.
8. Нужны заметки/комментарии (как минимум на item). Теги/сложные статусы не требуются.
9. Пользователь один, полноценная мульти-авторизация не нужна, но история изменений должна оставаться понятной.
10. Требование “все должно быть связано”: изменения количества в коробках и общего количества всегда синхронны; любые ошибки ловятся в момент операции; состояние не должно уходить в противоречивое.

## 1. Термины и смысл учета

### 1.1. SMART
`SMART` — идентификатор типа/модели запчасти из справочника parts DB. Это “что это за деталь”.

### 1.2. Item (экземпляр)
`Item` — **конкретная физическая штука** запчасти конкретного SMART.

У каждого item:
- есть SMART;
- есть текущее состояние (на складе, продано, списано и т.д.);
- есть текущая коробка (если item на складе);
- можно прикреплять фото/видео и заметки.

### 1.3. Box (коробка)
`Box` — место хранения. Коробка активна или закрыта.  
Закрытая коробка не участвует в выборе и не может содержать items на складе.

### 1.4. Operation (операция / событие)
Операция — это факт изменения состояния набора items: покупка, продажа, перемещение, возврат, списание, корректировка.

Операция нужна как:
- журнал (что было сделано, когда и почему);
- связь “почему item сменил состояние/коробку”.

---

## 2. Главный принцип: один источник истины

Чтобы не было противоречий, система должна иметь **один** источник истины для остатков.

### 2.1. Истина = items
Остатки считаются из `items`, а не из сумм по `movements`:

- Общий остаток SMART = `COUNT(items WHERE smart = X AND state = 'in_stock')`
- Остаток SMART в коробке = `COUNT(items WHERE smart = X AND state = 'in_stock' AND box = B)`

Это гарантирует отсутствие “минусов в коробке” по определению: нельзя продать то, чего нет как item.

### 2.2. Что тогда делать с текущей таблицей movements
Текущая модель (ledger `movements` + view `box_contents`) исторически полезна, но в item-модели она:
- либо становится legacy-историей,
- либо заменяется журналом `operations`.

Ключевое: **не должно быть ситуации**, когда:
- `items` говорят одно,
- а `movements` (или любые derived view) говорят другое,
и система пытается жить на обоих одновременно.

---

## 3. Непротиворечивость: инварианты (что БД обязана гарантировать)

Эти правила должны быть истинны всегда, иначе это “логическая ошибка системы”.

1. Item никогда не удаляется физически.  
   Только меняет `state`.
2. У item всегда есть `smart`, и smart существует в справочнике SMART.
3. Если `state = in_stock`, то:
   - `box` обязателен;
   - коробка должна быть активной.
4. Если коробка закрыта, то items со `state = in_stock` в ней быть не может.
5. Продажа/списание/минус-корректировка возможны только:
   - из выбранной коробки;
   - и только для реально существующих `items` в этой коробке со `state=in_stock`.
6. Transfer не меняет общий остаток, только переносит items между коробками.
7. Операции атомарны: либо применились полностью, либо не применились вообще.

Важно: эти инварианты лучше обеспечивать и кодом, и ограничениями/валидацией на уровне БД (CHECK/FK/NOT NULL + транзакции).

---

## 4. Идентификаторы items (чтобы “увидеть каждую запчасть”)

Каждый item должен иметь:

- `id` (технический ключ для ссылок/индексов);
- `item_code` — человекочитаемый код (например `EH-000001`) для поиска и наклеек.

Требования к `item_code`:
- уникален;
- не переиспользуется;
- генерируется детерминированно и последовательно.

UI/поиск должны позволять найти item по `item_code` и увидеть его историю и медиа.

## 5. Модель данных (концептуально)

Ниже не “DDL”, а смысл таблиц.

### 5.1. `boxes`
Реестр коробок (как сейчас), но инвариант: закрыть можно только пустую.

### 5.2. `items`
Экземпляры запчастей:
- `item_code`
- `smart`
- `box` (nullable, но только если item не на складе)
- `state` (`in_stock`, `sold`, `written_off`, …)
- `note` (заметка по конкретной штуке)
- timestamps

### 5.3. `operations`
Журнал операций (унифицированная сущность вместо “двух transfer строк” и т.п.):
- `type`: `purchase/sale/transfer/return/writeoff/adjust`
- `smart` (для удобства фильтрации, но источник истины все равно items)
- `qty` (сколько items затронуто)
- `box` или `from_box/to_box` (в зависимости от типа)
- `note` (комментарий операции)
- ссылки на заказ/отправку/возврат (если операция порождена ими)
- timestamps
- “удаление/отмена” (см. раздел 9)

### 5.4. `operation_items`
Связь операция ↔ конкретные items:
- `operation_id`
- `item_id`
Уникальность пары обязательна.

Это ключ для трассируемости: из операции всегда видно, какие items “ушли/пришли/переехали”.

### 5.5. `item_media` + хранение в PostgreSQL
Только item-level.

Метаданные:
- `item_id`
- `kind` (`photo`/`video`)
- `filename`, `mime`, `size_bytes`
- `sha256` (желательно)
- timestamps
- soft-delete поля

Данные в байтах:
- либо `data bytea` (для небольших файлов),
- либо хранение чанками `item_media_chunks(media_id, idx, data bytea)` (предпочтительно для больших видео).

Мы договорились: “нет лимитов”, но **техническая безопасность** обязательна (см. раздел 8).

## 6. Поведение операций (как именно “зациклено”)

### 6.1. Purchase (покупка)
Ввод: SMART, qty, коробка, цена (если нужно), note.

Эффект:
- создается операция `purchase`;
- создается `qty` новых items:
  - `state=in_stock`
  - `box=указанная коробка`
- связываем items с operation.

### 6.2. Sale (продажа)
Создается через заказы/отправки (как сейчас логически), но теперь операция должна работать на item-уровне.

Ввод: SMART, qty, коробка.  
Дополнительно: пользователь может выбрать **конкретные items** из этой коробки.

Эффект:
- выбираем `qty` items из указанной коробки со `state=in_stock`:
  - если пользователь выбрал вручную: берем именно их;
  - иначе применяем детерминированное правило (например FIFO по item_code/created_at).
- меняем им `state=sold`, `box=NULL` (или оставляем box как “последняя коробка”, но item не должен считаться “на складе”).
- создаем `sale` operation и `operation_items`.

Инвариант:
- невозможно продать больше, чем реально есть items в коробке.

### 6.3. Transfer (перемещение между коробками)
Ввод: SMART, qty, fromBox, toBox, note.  
Дополнительно: можно выбрать конкретные items вручную из fromBox.

Эффект:
- выбираем `qty` items в fromBox со `state=in_stock`;
- меняем им `box=toBox`;
- создаем `transfer` operation + `operation_items`.

Инвариант:
- общий остаток не меняется;
- fromBox и toBox активны;
- fromBox != toBox.

### 6.4. Writeoff (списание)
Ввод: SMART, qty, box, note.  
Выбор items: вручную или детерминированно.

Эффект:
- выбранные items меняют `state=written_off`, `box=NULL`;
- создаем `writeoff` operation + `operation_items`.

### 6.5. Adjust (корректировка)
Корректировка — это “исправление факта” (инвентаризация).

Adjust(+):
- создаем новые items в коробку.

Adjust(-):
- выбираем реальные items из коробки и переводим их в `state=written_off` (или отдельное состояние `adjusted_out`).

Важно: корректировка должна оставаться трассируемой: какие items добавили/убрали и почему.

### 6.6. Return (возврат) с отправки (shipment)
Требование: возвращается **та же самая запчасть**.

Следствие: shipment (или sale) должен иметь **конкретный список item_id**, которые ушли.

Возврат с shipment:
- пользователь выбирает, какие items возвращаются (обычно из shipment items списка);
- выбирает коробку, куда положить;
- items переводятся `state=in_stock`, `box=выбранная коробка`;
- создается `return` operation, привязанная к shipment/return сущности, + `operation_items`.

Инвариант:
- нельзя “вернуть” item, который не был в этой отправке/продаже;
- нельзя вернуть item, который уже возвращен/на складе.

---

## 7. Заказы, отправки, и связь с items

Сейчас система живет так:
- заказ создается → создаются движения sale → склад уменьшается;
- shipment меняет статус.

В item-модели важно:
- хранить соответствие “какие items ушли в этой продаже/отправке”.

Минимально нужно:
- при создании заказа/продажи фиксировать выбранные item_id;
- при создании shipment фиксировать item_id, относящиеся к shipment (если shipment’ов несколько).

Это необходимо для возврата “той же самой штуки” и для полной трассировки.

---

## 8. Медиа в PostgreSQL: требования “чтобы не было утечек и падений”

Мы храним медиа в PostgreSQL. При этом нельзя допустить:
- чтения/записи гигабайт в память процесса (memory blowup);
- подвисания UI/серверных обработчиков;
- повреждения данных (частично загруженный файл “притворился” валидным);
- ситуации, когда item удалили/изменили, а медиа осталось “подвешенным”.

Требования:
1. Загрузка должна быть потоковой (или через чанки), без удержания файла целиком в RAM.
2. Для каждого файла хранить метаданные + checksum (sha256).
3. Удаление медиа — через soft-delete (чтобы было понятно “что удалили”), плюс отдельная “очистка” при необходимости.
4. Отдача медиа:
   - минимум: скачивание;
   - желательно: потоковая отдача;
   - для больших видео потенциально нужен Range (обсуждается отдельно).
5. Системный предохранитель: даже если “нет лимитов”, сервер обязан корректно переживать ситуацию “место закончилось/БД распухла”.

## 9. Редактирование и удаление (операций/истории) без противоречий

Ранее требование: редактировать/удалять “движения” в истории.

В item-модели:
- “движение” = операция + список items.

### 9.1. Что значит “удалить”
Чтобы не терять понимание “что случилось”, удаление должно быть безопасным:

- По умолчанию “удалить” = пометить операцию как отмененную/удаленную (void) с причиной.
- При void операция перестает участвовать в расчетах (если мы вообще используем операции для отчетов), но главное:
  - состояние items должно быть корректно возвращено назад **только если это возможно без переписывания дальнейшей истории**.

### 9.2. Когда void разрешен
Void разрешен, если для каждого item из `operation_items`:
- после этой операции не было других операций, меняющих этот item.

Если были:
- void запрещен;
- вместо этого создается корректирующая операция (transfer/adjust/return/writeoff), которая приводит систему в нужное состояние без переписывания прошлого.

### 9.3. “Редактировать” как пользовательская функция
UI может давать “редактировать”, но реализация безопаснее через:
- void старой операции (если разрешено),
- создание новой операции (замены).

Так сохраняется понятность и не возникает “исчезли вещи без следа”.

---

## 10. Неактивные коробки и запреты

Требование: “для неактивных не может быть”.

Значит:
- нельзя создать/переместить item в закрытую коробку;
- нельзя закрыть коробку, если в ней есть items со `state=in_stock`;
- нельзя выбрать закрытую коробку в любом селекторе.

Это должно быть обеспечено и на фронте (скрыть/задизейблить), и на бэке/в БД (проверки).

---

## 11. Страница истории (/history) в новой модели

`/history` должна показывать историю операций (а не только агрегатные qty-строки), и позволять:

- открыть операцию и увидеть:
  - тип операции
  - коробки (from/to)
  - note
  - список item_code/item_id
  - связь с заказом/отправкой/возвратом
- выполнить “редактирование” (через void+replace, если допустимо)
- выполнить “удаление” (void), если допустимо

Для операций, связанных с заказами/отправками:
- управление лучше делать из заказа/отправки (чтобы не ломать бизнес-процесс),
- но история должна быть читаема и кликабельна.

## 12. Инициализация/миграция от текущей системы

Требование: “все должно быть сразу грамотно” и допускается удаление.

Поскольку текущая система хранит количества, а не экземпляры, полностью восстановить “какая именно штука куда ходила” задним числом невозможно.

Поэтому есть два честных пути:

### Путь A (самый чистый): перезапуск учета на items
1. Сделать бэкап текущей inventory БД.
2. Очистить/пересоздать учет так, чтобы новая система стартовала без противоречий.
3. Провести физическую инвентаризацию и занести реальные items по коробкам.
4. С этого момента учет ведется строго в item-модели.

Плюсы:
- нет legacy-расхождений;
- все “сразу грамотно”;
- дальше проще поддерживать.

Минусы:
- старую историю надо хранить отдельно (в бэкапе/архиве) или перенести как “архивные отчеты”.

### Путь B (компромисс): snapshot текущего состояния в items
1. Берем текущие вычисленные остатки по коробкам и SMART.
2. Создаем items на основе этого snapshot.
3. Проблемы `unboxed/overboxed` надо решать явно:
   - либо через специальную “коробку неопределенного места”,
   - либо через ручную инвентаризацию до нуля расхождений.

Плюсы:
- меньше ручной работы на старте.

Минусы:
- риск тащить исторические неточности дальше.

В рамках требования “никаких противоречий” предпочтителен Путь A.

---

## 13. Тестирование и контроль качества (чтобы не пропало и не сломалось)

### 13.1. Автоматические проверки инвариантов
Должны быть тесты/проверки, которые гарантируют:
- закрытая коробка не содержит items in_stock;
- нельзя продать item не из указанной коробки;
- нельзя продать/списать больше items, чем реально есть;
- transfer не меняет общий остаток, только box;
- return с shipment возвращает ровно те items, которые были в shipment;
- void/replace не оставляет “подвешенных” items.

### 13.2. E2E сценарии (ручные/agent-browser)
- покупка → медиа → перемещение → продажа → shipment → возврат той же item → проверка, что item вернулась и медиа сохранилось;
- попытка закрыть коробку с items → блок;
- попытка выбрать закрытую коробку → невозможно;
- попытка удалить операцию “из середины цепочки” → блок + понятная ошибка.

---

## 14. Итог

Целевая система строится вокруг **экземпляров** (`items`) и их жизненного цикла.

Это обеспечивает:
- отсутствие противоречий (нельзя “продать воздух”);
- ясность, где находится каждая штука;
- возможность хранить медиа именно для конкретной запчасти;
- корректные возвраты “той же самой штуки” с отправки;
- историю, где всегда понятно, что случилось и почему.
